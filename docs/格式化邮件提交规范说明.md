# 邮件附件提交规范说明

更新时间：2026-05-03

## 当前目标

邮件渠道现在按“用户上传材料完全一致的主链路”收口，不再要求正文提供任何结构化元数据。

本规范只回答三件事：

1. 系统如何从主题中匹配任务标识；
2. 正文和附件的最小约束是什么；
3. 邮件进入系统后与普通上传链路的关系是什么。

## 总体原则

1. 邮件只是附件上传入口，不在邮件正文里重复定义材料类型、成员编号或其他业务字段。
2. 任务标识只从邮件主题开头的尖括号中解析。
3. 邮件正文是自由文本；可以为空，也可以写任意说明，系统不会按固定格式解析。
4. 附件进入后端时，默认按普通上传缺省行为落为 `other_attachment`，后续继续走现有识别、人工改类型、归票和校验主链路。
5. 成员身份仍只来自受信任入站器提供的 `resolved_member_id` 或已绑定发件人邮箱，不放宽成员绑定边界。

## 主题格式

邮件主题必须以尖括号任务标识开头，例如：

```text
<ccny2026>Fw: 中国南方航空全电发票（全面数字化电子发票）
```

规则：

1. 只解析主题开头第一个尖括号中的内容。
2. 尖括号中的任务标识必须非空，且不能包含空白字符。
3. 尖括号之后的回复/转发前缀和原始标题都原样保留，不参与机器解析。

以下情况视为主题格式错误：

1. 主题不是以 `<task_key>` 开头；
2. 尖括号内为空；
3. 尖括号内包含空白字符。

## 正文规则

1. 正文不要求任何固定格式。
2. 正文可以为空。
3. 系统不会再解析 `material_type`、`submitter_id`、`task_id`、`note` 等键值对。
4. 正文内容不会参与权限判断、任务匹配或材料类型判定。

## 附件规则

1. 一封邮件必须至少包含一个普通附件。
2. 附件的大小、内容类型、空文件和文件名校验，沿用统一材料上传规则。
3. 邮件内联图片如果没有独立文件名或只是正文装饰资源，默认不作为提交材料。
4. 若一封邮件同时包含合法附件和非法附件，仍沿用现有批量上传的“部分成功”语义。

## 处理结果与失败原因

邮件接入至少稳定返回或记录以下失败原因：

| 失败码 | 场景 |
|---|---|
| `invalid_subject_prefix` | 主题不是以 `<task_key>` 开头 |
| `missing_task_id` | 尖括号中的任务标识为空或包含空白 |
| `missing_attachments` | 邮件没有可处理附件 |
| `attachment_missing_filename` | 某个附件缺少文件名 |

以下情况不属于“格式错误”，应进入既有业务边界：

1. 主题中的任务标识合法，但系统内查不到任务：
   - 进入待归属材料；
   - 保留 `task_id_hint=<subject task_key>`。
2. 发件人邮箱未绑定成员身份：
   - 进入待归属材料；
   - 保留 `submitter_id_hint=email:<sender>`。
3. 发件人已绑定成员，但不属于目标任务：
   - 走统一成员权限校验失败路径；
   - 不由邮件接入器自定义特判。

## 与普通上传链路的一致性

邮件附件一旦通过主题和附件校验，就直接复用现有统一材料上传服务：

1. 已解析到可信成员身份时，进入任务内已归属材料主链路；
2. 未解析到可信成员身份或任务不存在时，进入待归属材料主链路；
3. 材料默认类型与普通上传未显式选择类型时一致，都是 `other_attachment`；
4. 后续识别任务占位、对象存储、重复文件检测、管理员改类型、归票和校验逻辑都与普通上传保持一致。
