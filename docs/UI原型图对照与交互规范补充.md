# UI 原型图对照与交互规范补充

更新时间：2026-04-29

本文档基于 `docs/原型图.png` 与当前 Web 前端实现整理，目的不是要求前端逐像素复刻原型图，而是明确第一阶段 UI/交互必须遵循的基本规范，并指出当前实现中不合理、易用性不足或与业务主流程错位的部分。

## 1. 适用原则

当前 UI 后续迭代应遵循以下原则：

1. 不要求完全复刻原型图的视觉细节、卡片阴影、字号和具体布局比例。
2. 必须遵循原型图体现出来的基础信息架构、主流程顺序和操作闭环。
3. 优先保证“用户一眼知道现在处于什么阶段、下一步要做什么、哪里有异常”。
4. 优先减少跨页面跳转和上下文丢失，而不是继续按后端接口边界拆很多独立页面。
5. 页面文案应面向报销业务，不应持续暴露“导出占位”“在线预览”“页面边界”这类偏实现视角的说明。

## 2. 原型图体现的基础规范

从原型图可以抽出以下必须遵循的交互规范：

### 2.1 管理端应以“任务推进”而不是“页面入口”组织

原型图顶部把流程明确画成：

1. 创建任务
2. 发布任务
3. 材料收集流程
4. 审核异常
5. 分摊与确认
6. 导出提交
7. 成员提交
8. CLI 提交

这意味着 UI 的主组织方式应是“任务当前推进到哪一步”，而不是让用户先理解站点有哪些页面。

### 2.2 管理端应有稳定导航骨架

原型图左侧管理导航至少体现了这些稳定模块：

- 首页 / 总览
- 任务管理
- 材料审核
- 成员管理
- 预算分配 / 分摊
- 导出与打印
- 系统设置
- 日志审计

这不代表当前阶段必须把所有功能一次做完，但至少要保持“固定导航 + 当前所在模块 + 当前任务上下文”的稳定结构，而不是只有顶栏角色入口。

### 2.3 关键页面应采用“列表 + 详情/侧栏”的审查模式

原型图中的材料审核页，不是把所有信息铺成长列表，而是：

- 左侧表格集中展示材料列表和状态标签；
- 右侧详情面板展示单张票据、原图、校验结果和待处理动作。

这说明审核类页面的主交互应是“先在列表中筛选，再在同页完成查看和处理”，而不是在多个页面之间来回切换。

### 2.4 成员端应形成单次提交闭环

原型图里的成员提交页把以下动作放在同一上下文中：

- 选择任务
- 上传票据 / 附件
- 查看 AI 识别结果
- 选择费用归属
- 填写分摊金额
- 查看必传材料清单
- 直接提交

这说明成员端的核心目标不是“分别去上传页、状态页、确认页”，而是尽量在单一任务上下文中完成一次报销材料处理闭环。

### 2.5 状态表达应统一且可扫描

原型图通过统一颜色表达：

- 绿色：通过
- 黄色：待补充
- 红色：异常
- 蓝色：进行中
- 灰色：已结束 / 不可操作

因此页面状态应尽量统一表达，不应让同一含义在不同页面出现多套标签体系。

## 3. 当前 UI 设计的不合理之处

以下问题来自对当前前端实现的静态阅读，不等同于视觉审美判断，而是业务流程与交互结构层面的明显不合理。

### 3.1 首页仍然偏“入口页”，不是任务推进页

当前首页和角色入口收口后虽然比之前干净，但核心仍是“进入哪个工作台”，而不是“当前任务推进到哪里”。用户首先看到的是工作台概览、角色说明和入口，而不是：

- 我当前有哪些报销任务；
- 哪个任务最紧急；
- 缺什么材料；
- 哪些成员未确认；
- 下一步应该做什么。

这与原型图强调的“按任务阶段推进”不一致。

### 3.2 管理端缺少稳定的功能导航骨架

当前管理端主要依赖：

- 顶部总导航；
- 各页面内部的返回链接；
- 任务详情页中的一组跳转按钮。

这会导致管理员在“任务详情 / 发票录入 / 分摊编辑 / 复核 / 导出”之间切换时，上下文不断被重建。原型图体现的是稳定的管理骨架和模块定位，而不是每个页面各自放一排链接。

### 3.3 任务上下文被拆散到过多独立页面

当前一个管理员想处理一个任务，往往要跳转：

- 任务详情
- 发票录入
- 缺失材料
- 复核总览
- 费用分摊
- 导出管理

这些页面分别存在，但整体过于碎片化。原型图中的关键思想是：围绕同一个任务，在尽量少的上下文切换中完成任务推进，而不是把任务拆成一组离散工具页。

### 3.4 材料审核页缺少同页详情联动

原型图中的材料审核异常页具备强烈的“表格 + 右侧详情”结构，便于快速扫表、点开、修正。

当前实现虽然已有复核总览和发票编辑页，但没有形成明确的：

- 左侧材料列表筛选
- 右侧当前选中票据详情
- 同页查看原件、识别字段、校验结果和处理动作

因此审核动作仍然偏重跳页和上下滚动，效率不高。

### 3.5 成员端闭环被拆成“上传 / 状态 / 缺失 / 费用确认”四段

当前成员端主要分成：

- 任务列表
- 材料上传
- 材料状态
- 缺失材料
- 费用确认

这比“全堆到一个页面”更清晰，但仍然不符合原型图体现的最小闭环。对于普通成员来说，更自然的目标是“我选一个任务，然后把这张票处理完”，而不是先理解自己要去哪一个子页面。

### 3.6 成员看不到完整的当前发票处理上下文

你已经额外提出：

- 用户应能查看和修改自己上传的发票内容；
- 用户应能看到材料类型；
- 用户应能看到金额分配给谁；
- 同一比赛任务中的成员之间应可查看当前已上传发票。

当前实现还明显缺少这一层完整上下文。成员页虽然能看到本人材料状态和部分录入字段，但仍没有稳定形成“当前发票详情 + 分摊去向 + 关联附件 + 异常原因 + 下一步动作”的一体化视图。

### 3.7 页面文案仍然泄露实现视角

当前若干页面仍保留较强的实现导向描述，例如：

- “PDF 合并计划占位”
- “在线预览”
- “页面边界已收口”
- “这里只列出你可以查看的任务”

这些文案在开发阶段可以帮助区分功能边界，但不适合作为长期的业务界面主文案。原型图的文案风格明显更偏“任务、票据、异常、确认、导出”这些业务实体。

### 3.8 状态标签和摘要结构还不够统一

当前项目已经有 `StatusBadge`、统计卡片和任务摘要，但不同页面的状态表达仍不完全统一：

- 有的地方按识别状态；
- 有的地方按校验状态；
- 有的地方按确认状态；
- 有的地方又使用实现导向的“占位 / 在线预览 / 已收口”。

原型图的优势在于：即使用户不懂技术实现，也能快速识别哪些是绿色、黄色、红色的待处理项。

## 4. 后续 UI 文档与实现应遵循的规则

### 4.1 管理端

1. 管理端必须围绕“当前任务推进状态”组织首页和任务详情。
2. 管理端应逐步收口为稳定导航骨架，而不是继续增加零散页面跳转按钮。
3. 审核类页面优先采用“列表 + 详情面板”模式。
4. 缺失材料、异常校验、待确认成员和导出准备度应在同一任务上下文中可连续查看。

### 4.2 成员端

1. 成员端应逐步收口为“按任务处理当前票据”的闭环，而不是持续拆成多个弱关联页面。
2. 成员必须能稳定看到自己发票的识别字段、人工更正值、材料类型、分摊去向和缺失材料要求。
3. 按最新产品要求，同任务成员间可查看当前已上传发票的基础元数据与分摊去向，但敏感原始附件访问边界仍需单独定义。
4. AI 识别结果、必传材料清单和分摊信息应尽量出现在同一任务/票据上下文中。

### 4.3 文案与状态

1. 主文案优先描述业务动作，不优先描述技术边界。
2. 状态颜色和标签应统一。
3. 默认先告诉用户“现在有什么问题、要做什么”，再解释底层实现原因。
4. 开发占位信息只能保留在内部说明或调试入口，不应长期停留在主业务界面。

## 5. 当前结论

当前前端已经从“暴露内部实现名词和多角色混杂入口”的状态前进了一步，但离原型图体现的“任务驱动、单页闭环、列表联动详情、状态一眼可扫”的基本规范仍有明显距离。

后续 UI 迭代不应以“把每个独立页面再润色一点”为目标，而应优先做以下结构性调整：

1. 收口管理端导航和任务推进总览。
2. 把材料审核做成列表联动详情。
3. 把成员端收口为单任务下的材料处理闭环。
4. 把发票元数据、分摊信息和异常提示放回同一上下文。
5. 按统一状态语言和统一视觉语义重写页面文案。
