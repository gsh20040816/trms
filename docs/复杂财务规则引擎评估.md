# 复杂财务规则引擎评估

更新时间：2026-04-29

## 1. 评估目标

本评估用于回答两个问题：

1. 当前第一阶段的发票校验模块是否已经需要迁移到“配置化规则”或 DSL；
2. 如果未来要迁移，触发条件和最小迁移边界是什么。

本轮只做评估，不引入新依赖，不改动现有业务规则实现。

## 2. 当前实现现状

当前规则主入口位于 `src/trms_backend/domain/invoice_validation.py`，核心形态是“纯函数 + 常量 + 统一 `ValidationResult` 输出”：

- `validate_invoice()` 顺序执行各条规则，并返回统一结构结果；
- 阈值、适用费用类型、字段组和匹配策略直接定义在模块级常量中；
- 规则本身主要依赖 `InvoiceRecord`、`ReimbursementTask`、识别结果和附件列表，不依赖数据库或外部服务；
- `tests/test_invoice_validation_rules.py` 已覆盖现有高优先级规则的通过 / 失败 / 待确认矩阵。

按当前代码，第一阶段已经落地的规则仍以固定业务不变量为主，例如：

- 抬头 / 税号匹配；
- 发票号码重复；
- 满额支付记录必需与金额匹配；
- 参赛费比赛通知必需；
- 航空行程单 / 舱位证明；
- 网约车行程信息；
- 比赛时间和地点范围。

## 3. 当前结论

结论：**现在还不应该直接引入 DSL，也不应该为了“未来可扩展”先上独立规则引擎。**

原因如下：

1. 当前规则数量仍有限，且大多是明确、稳定、可由代码直接表达的不变量。
2. 现有实现已经具备统一结果模型和独立规则函数，维护成本仍可控。
3. 真正的痛点目前不是“不会写新规则”，而是“阈值、适用范围、字段映射和组织差异都写死在单文件里”。
4. 如果此时直接引入 DSL，会先增加解释器、配置校验、调试和审计复杂度，但还没有真实收益证明这些成本值得支付。

因此，当前更合理的判断是：

- **短期继续保持代码规则；**
- **中期先把“可配置的策略参数”从规则代码中剥离；**
- **只有在配置化仍不足以承载复杂差异时，才进入 DSL。**

## 4. 已识别的现有限制

当前实现最明显的扩展压力主要有四类：

1. 模块级常量硬编码：
   - 例如支付记录阈值、比赛时间缓冲天数、支持校验的费用类型。
2. 识别字段别名硬编码：
   - 例如舱位字段组、地点字段组、网约车判定字段和真假值集合。
3. 规则适用条件写死在函数分支中：
   - 例如“注册费必须有比赛通知”“机票必须有行程单”。
4. 匹配策略固定：
   - 例如支付记录只支持 `exact_sum`，地点范围只支持当前的字符串归一化包含匹配。

这些限制说明：当前最需要的不是 DSL，而是把“策略参数”和“规则执行代码”分层。

## 5. 迁移触发条件

只有当以下任一情况持续出现时，才建议把当前代码规则继续上提为“配置化规则”或 DSL：

### 5.1 先触发配置化的条件

满足以下任一项，就应优先做“配置化策略”而不是继续堆模块常量：

1. 同一条规则需要按比赛类型、学院、项目经费来源或任务模板切换阈值。
2. 非开发人员需要调整阈值、缓冲天数、适用费用类型或字段映射，且调整频率达到月级。
3. 相同规则在多个模块重复维护同类常量，已经出现漂移风险。
4. 为了新增一个费用类型或附件类型，必须同时改动 3 处以上硬编码分支。

### 5.2 再触发 DSL 的条件

只有在“配置化策略”已经落地后，仍满足以下任一项，才建议评估 DSL：

1. 规则之间开始出现显式依赖、优先级编排或短路逻辑，单纯函数顺序难以维护。
2. 需要由运营或管理员在不发布代码的前提下新增整条规则，而不是只改阈值。
3. 同一类规则需要表达嵌套布尔条件、规则组、例外条款和版本化生效时间。
4. 规则执行解释、审计回放和“为什么命中此规则”的需求已经超过当前 `evidence` 能力。

如果只是“规则会继续增多”，但新增规则仍能稳定写成纯函数，那么还不构成 DSL 触发条件。

## 6. 建议的最小演进路径

建议按以下顺序推进，避免一次性过度设计：

1. 第一步：提炼 `ValidationPolicy`
   - 把阈值、缓冲天数、费用类型集合、字段组、匹配模式等参数从模块常量挪到单独的 Python 配置对象。
2. 第二步：支持任务级或模板级策略覆盖
   - 保持规则函数不变，只让调用方注入不同策略。
3. 第三步：为策略建立版本号和审计边界
   - 让校验结果可追溯“当时使用的是哪一版策略”。
4. 第四步：只有在规则本体也需要动态定义时，再评估 DSL
   - DSL 只负责表达规则，不负责替代现有权限、识别、审计和状态流转逻辑。

## 7. 当前保守建议

基于第一阶段范围和当前代码复杂度，当前保守建议是：

- 继续沿用代码规则模型；
- 后续若先出现阈值/字段映射/费用类型差异化需求，先拆“配置化策略”任务；
- 在没有真实动态规则维护需求前，不要引入 YAML 规则文件、自定义表达式解释器或第三方规则引擎。

这符合本仓库当前的优先级：先保证正确性、可验证性和可维护性，再考虑抽象升级。
