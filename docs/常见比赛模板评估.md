# 常见比赛模板评估

日期：2026-04-29  
范围：第一阶段是否引入“常见比赛模板”能力的评估，不直接实现功能

## 结论

- 不进入第一阶段实现范围。
- 归入后续阶段增强项，但应与“历史成员信息复用”分开建模，避免把模板预填和成员主数据复用混成一条脏路径。

## 评估依据

1. 需求文档 `同济大学ACM竞赛报销收集系统需求分析文档_V0.2.md` 第 14.3 节已将“常见比赛模板”列为 Could have，而不是第一阶段 Must / Should。
2. 架构文档 `同济大学ACM竞赛报销收集系统架构设计与技术选型文档_V0.1.md` 第 13.3 节已将“历史比赛模板和成员复用”归入后续阶段能力。
3. 当前创建链路是“管理员显式填写任务字段”的最小闭环：
   - 后端 `TaskCreateInput` 直接要求比赛名称、地点、起止日期、成员名单、费用类别、管理员、截止时间、项目和报销人信息；
   - 前端 `web/src/app/admin-task-create.tsx` 也是逐字段录入，没有模板选择、模板预填、模板版本或覆盖语义。

## 模板可能包含的字段与使用场景

如果后续要做，“比赛模板”更适合作为创建任务时的一次性预填工具，而不是新的任务事实来源。较合理的模板字段边界如下：

1. 可预填字段：
   - 比赛名称的固定前缀或系列名称；
   - 常见比赛地点；
   - 常用费用类别组合；
   - 项目/报销人信息的建议填写结构或默认文案；
   - 材料提醒说明或管理员备注模板。
2. 不应直接进入模板的字段：
   - `member_ids`，这属于成员复用或成员主数据问题；
   - `administrator_id`，当前创建权限和责任人必须来自当前登录上下文；
   - 比赛具体日期、截止时间，这些是每次任务都强时效变化的字段；
   - 发票抬头、税号，这两个字段已有全局配置继承边界，不应再引入一套模板来源与之竞争。
3. 典型使用场景：
   - 同类比赛反复举办时，减少管理员重复填写地点、费用类别和项目说明；
   - 不改变当前“创建后仍需人工核对任务关键信息”的流程。

## 当前不适合进入第一阶段的原因

1. 当前主路径已经足够紧凑，再加模板会引入新的来源合并语义。
   管理员现在只需填写一个表单并直接创建任务。若引入模板，就必须定义“先选模板再编辑”还是“创建后套模板”、哪些字段允许覆盖、哪些字段必须保留手填，这会扩大当前最小创建闭环。
2. 模板与全局配置、历史成员复用边界容易混淆。
   发票抬头/税号已经由全局配置控制；成员名单复用又是独立后续能力。如果现在直接上模板，很容易把“全局默认值”“模板默认值”“历史成员回填”三套来源糊在一起，增加排障和权限语义复杂度。
3. 第一阶段收益主要是录入提效，不是主链路阻塞项。
   现有第一阶段更关键的是保证提交、识别、校验、分摊、确认和导出稳定。模板只优化管理员录入速度，不解决当前主链路正确性或安全性问题。
4. 模板一旦落库，就会带来版本和演进负担。
   需要回答模板是否允许修改、旧任务是否受影响、删除模板如何处理、模板字段扩展如何迁移。对当前“单轮最小可验证任务”而言，这明显超出范围。

## 后续阶段建议边界

若后续要做，建议按以下顺序拆任务，而不是直接改现有创建页：

1. 先建立只读模板模型。
   模板只表达“建议默认值”，不自动修改既有任务，也不承担成员主数据职责。
2. 再支持创建页一次性应用模板。
   管理员选择模板后，仅对当前未填写字段做预填，或显式提示将覆盖哪些字段，避免隐式合并。
3. 最后再评估与历史成员复用的联动。
   只有在成员主数据边界清楚后，才考虑“模板 + 常见成员名单”的组合能力，避免把两个后续增强项提前缠在一起。
