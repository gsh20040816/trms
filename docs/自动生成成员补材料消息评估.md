# 自动生成成员补材料消息评估

日期：2026-04-29  
范围：第一阶段是否引入“自动生成成员补材料消息”能力的评估，不直接实现功能

## 结论

- 不进入第一阶段实现范围。
- 归入后续阶段增强项；当前仓库可保留“自动提醒任务快照”作为管理员侧待处理线索，但不应把它误写成“系统已经自动向成员发出消息”。
- 若后续要做，必须先建立独立通知模块或通知出站边界；不能直接在现有 `automatic_reminder_tasks` 记录上叠加隐式发信逻辑。

## 评估依据

1. 需求文档 `同济大学ACM竞赛报销收集系统需求分析文档_V0.2.md` 第 14.3 节已将“自动生成成员补材料消息”列为 Could have，而不是第一阶段 Must / Should 主链路。
2. 同一需求文档在 FR-009 中要求的是“管理员可手动提醒成员补材料”和“管理员可查看自动提醒记录”，没有把“真实自动发送通知”列为第一阶段验收门槛。
3. 当前验收映射 `docs/第一阶段验收映射.md` 已明确：
   - AC-017 当前已完成的是“缺失材料聚合、提醒记录和相关导出”；
   - 缺口仍是“自动发送提醒与消息模板仍未实现”。
4. 当前仓库已有两类接近的能力，但都还不是通知系统：
   - `src/trms_backend/domain/material_reminders.py` 只记录管理员手动填写的补材料提醒文本；
   - `src/trms_backend/domain/automatic_reminders.py` 只根据缺失材料和未确认费用生成 `pending` 状态的提醒任务快照。

## 当前代码现状

当前实现已经能回答“谁需要被提醒、因为什么被提醒”，但还不能回答“通过什么渠道、以什么模板、何时真正发出消息”。

1. 自动提醒候选已经存在，但仅是待处理记录。
   `POST /api/tasks/{task_id}/automatic-reminder-tasks` 会按当前任务快照生成 `missing_materials` 和 `unconfirmed_expenses` 两类记录，并做幂等去重；这些记录只保存在数据库，不会触发任何外部发送器。
2. 管理员人工提醒已经存在，但仅是文本留痕。
   `POST /api/tasks/{task_id}/material-reminders` 允许管理员填写自由文本提醒内容，并在后台页面查看记录；它仍然不会自动发送到成员邮箱、Telegram 或其他渠道。
3. 当前没有通知模块。
   仓库内不存在统一的通知出站接口、消息模板渲染器、发送队列、重试状态机、送达回执模型或渠道适配器。
4. 当前可用渠道也不具备稳定的主动通知闭环。
   - Web 端当前更适合“成员主动登录后查看缺失材料和状态”，不是服务端主动推送；
   - Telegram、格式化邮件当前只有入站材料接收边界，没有出站消息确认链路；
   - CLI 是 pull 型工具，成员通过 `tasks`、`status`、`missing-materials` 主动查询，不是长连接通知客户端。

## 消息模板建议边界

如果后续要做，消息模板应保持“结构化事实 + 明确下一步动作”，不要直接把 AI 识别文本或管理员自由备注整段原样外发。

建议最小模板字段如下：

1. 固定抬头：
   - 任务名称；
   - 成员编号或姓名展示名；
   - 触发时间；
   - 提醒来源：系统自动生成或管理员确认后发送。
2. 缺失材料主体：
   - 涉及的发票编号或费用摘要；
   - 缺失的材料类型列表，例如 `payment_record`、`competition_notice`；
   - 缺失原因摘要，例如“大额发票缺少支付记录”“报名费缺少比赛通知”。
3. 动作指引：
   - 建议成员去哪个页面或命令补交；
   - 当前任务截止时间；
   - 若任务已关闭，提示联系管理员重新开放。
4. 风险提示：
   - 提醒内容仅代表当前系统快照，后续管理员更正或成员补交后状态可能变化；
   - 不在消息正文中外发原始发票全文、支付截图全文或无关成员信息。

不建议直接允许模板拼接以下内容：

1. 原始票据图片或支付截图全文。
2. 无关成员的分摊详情。
3. 未经人工确认的高风险推断结论，例如“你的报销一定会被拒绝”。

## 渠道边界

“自动生成消息”与“自动发出消息”必须分开建模。当前更合理的后续顺序是：先生成标准化提醒载荷，再选择有限渠道出站。

建议的渠道优先级：

1. Web 站内提醒或任务工作台内提示。
   这是与当前系统最一致的方案，因为成员已经能在 Web 页面查看缺失材料和下一步动作，不需要额外引入第三方渠道可信性问题。
2. 邮件通知。
   仅在真实邮箱绑定和出站发信配置完整后考虑；否则无法确认提醒是否真的送达给正确成员。
3. Telegram 通知。
   仅在 Telegram 绑定链路和出站 Bot 权限稳定后考虑；当前仓库只有入站可信 token 边界，不具备可审计的出站确认闭环。
4. CLI 不建议作为 push 渠道。
   CLI 更适合继续保留 pull 模式，让成员执行查询命令读取最新状态，而不是在本地维持后台通知守护进程。

## 审计要求

该能力如果真的实现，必须依赖正式审计链路，不能只有“发过了”这一句模糊日志。

至少应审计以下字段：

1. 谁触发了提醒。
   是系统按规则自动生成，还是管理员手动确认后发送。
2. 为谁发送。
   目标成员、目标任务、目标提醒类别。
3. 发了什么版本的内容。
   使用的模板版本、结构化 payload 摘要、是否附带管理员附言。
4. 通过什么渠道发送。
   Web 站内、邮件、Telegram 等。
5. 发送结果如何。
   已排队、发送成功、失败、重试中、永久失败。
6. 是否被撤回或作废。
   当成员已经补材料、任务关闭或管理员重新判断后，旧提醒是否应停止继续发送。

在当前 `AC-018 审计记录` 仍未完成的前提下，直接接入真实自动通知会放大“无法追溯谁向谁发了什么”的风险。

## 当前不适合进入第一阶段的原因

1. 第一阶段主链路已经有更低风险的替代手段。
   成员当前可以在 Web 工作台和 CLI 查询缺失材料，管理员也能记录人工提醒；自动外发通知提升的是催办效率，不是主链路正确性阻塞项。
2. 它天然依赖一个当前仓库并不存在的通知模块。
   需要模板渲染、出站适配、失败重试、限流、去重、送达状态和撤回策略，这不是在现有任务接口上补一个字段就能收口的增强。
3. 渠道身份边界当前还不够稳。
   Telegram、邮件目前主要解决的是材料入站可信性，而不是成员出站通知身份确认；如果现在直接发消息，很容易把提醒发给错误对象或形成无法追责的旁路。
4. 审计要求尚未满足。
   当前系统连统一审计日志主链路都还没完成，先上自动通知会让“谁触发、发给谁、发了什么、失败怎么办”都处于半透明状态。

## 后续阶段建议边界

如果后续要推进，建议按下面的最小顺序拆任务：

1. 先建立通知域模型。
   明确 `notification/outbox`、模板版本、发送状态、渠道适配和重试策略。
2. 再把 `automatic_reminder_tasks` 收口成“提醒候选快照”。
   它只负责生成结构化提醒事实，不直接负责出站。
3. 先实现 Web 站内提醒。
   这一步外部依赖最少，也最容易与当前成员工作台闭环。
4. 审计链路完成后，再评估邮件或 Telegram 外发。
   没有正式审计前，不应扩展到第三方主动通知渠道。

## 本轮决定

- 第一阶段维持现状：继续保留缺失材料聚合、自动提醒任务快照和管理员手动提醒记录，不实现真实自动发消息。
- 后续如要推进，应先新增“通知模块与补材料提醒出站模型设计”任务，而不是直接在现有自动提醒接口里触发消息发送。
