# 数据库迁移策略说明

更新时间：2026-04-28

## 当前事实

当前仓库已引入 Alembic 作为 schema migration 工具，并建立了首个基线迁移 `20260428_01`。

数据库初始化当前分成两条路径：

- 位置：`src/trms_backend/infrastructure/database.py`
- 调用入口：`src/trms_backend/main.py`
- Alembic 配置：`alembic.ini`、`alembic/env.py`、`alembic/versions/`
- 默认数据库：本地 SQLite `sqlite:///./trms.db`
- 测试数据库：各 pytest 用例使用临时 SQLite 文件

运行边界如下：

1. 开发和测试环境仍允许 `Base.metadata.create_all(...)` 自举空库，便于本地开发、pytest 和临时 SQLite 快速启动。
2. 生产环境 API 和 worker 启动时不再调用 `create_all` 自动建表或自动演进 schema。
3. 生产环境数据库必须先执行 `alembic upgrade head`；若 schema 未迁移到当前 head，服务启动会显式失败。
4. `./scripts/verify.sh` 现在会对临时 SQLite 数据库执行 `upgrade head -> downgrade base -> upgrade head`，验证迁移脚本至少可执行。

## 当前仍保留的限制

虽然已接入 Alembic，但当前迁移机制仍有明确边界：

1. 当前只有基线迁移，尚未经历真实的增量 schema 演进和数据回填场景。
2. 开发/测试环境保留 `create_all` 只用于本地自举，不能被误解为共享环境迁移方式。
3. 旧的本地 SQLite 库如果是历史 `create_all` 生成，未必存在 `alembic_version`；这类库需要先人工处理，不能直接假设可安全升级。
4. 目前验证脚本只覆盖 SQLite 临时库，不等同于 PostgreSQL 生产迁移已经演练完成。

## 第一阶段决策

本轮决策如下：

1. 共享环境正式切换到 Alembic 管理 schema，不再依赖应用启动期 `create_all`。
2. 开发/测试环境继续保留 `create_all` 自举能力，避免当前大批 pytest 和临时 SQLite 开发流被迫先跑迁移命令。
3. 首个 Alembic revision 只表达“当前 schema 基线”，不在本轮掺入额外数据迁移或结构重构。
4. 对已有本地旧库，优先建议备份后重建；只有在确认结构与基线一致时，才允许 `alembic stamp head`。

这样做的原因是：

1. 当前任务队列已经进入生产化阶段，继续依赖 `create_all` 会让共享环境 schema 演进不可审计。
2. 仓库已出现足够多的表、索引和约束，后续再无基线地引入迁移，成本只会更高。
3. 直接删除开发/测试自举能力会扩大本轮影响面，不符合“单轮只做一个最小任务”的约束，因此保守保留本地自举边界。

## 推荐操作

### 新环境建库

1. 配置 `DATABASE_URL`。
2. 执行 `uv run alembic upgrade head`。
3. 再启动 API 或 worker。

### 本地旧库处理

1. 若旧 SQLite 数据不需要保留：删除旧库，重新执行 `alembic upgrade head`。
2. 若必须保留：先备份，再人工核对 schema 是否与当前基线一致。
3. 只有在“已确认结构一致”前提下，才可执行 `uv run alembic stamp head`；否则应先设计专门的数据迁移 revision。

### 后续增量演进要求

1. 后续任何 schema 变更都应新增独立 Alembic revision，不再依赖 `create_all` 补表。
2. 涉及数据回填、列重命名、约束调整时，必须在 revision 中显式表达 upgrade/downgrade 策略。
3. PostgreSQL 上线前，仍需补一轮真实 PostgreSQL 迁移演练；当前不能把 SQLite 验证等同于生产数据库验证。
