# 数据库迁移策略说明

更新时间：2026-04-28

## 当前事实

当前仓库没有引入 Alembic 或其他 schema migration 工具。

数据库初始化方式为应用启动时执行 `Base.metadata.create_all(...)`：

- 位置：`src/trms_backend/infrastructure/database.py`
- 调用入口：`src/trms_backend/main.py`
- 默认数据库：本地 SQLite `sqlite:///./trms.db`
- 测试数据库：各 pytest 用例使用临时 SQLite 文件

该策略适合当前第一阶段的小规模本地开发和测试启动，优点是：

- 不需要额外迁移命令即可创建缺失表；
- 对当前仓库“表数量少、开发者少、测试数据库可重建”的现状成本最低；
- pytest 使用临时 SQLite 文件时，能够直接依赖应用启动完成建表。

## 当前策略的限制

`create_all` 只能补齐不存在的表，不提供可靠的版本化 schema 演进能力。当前限制包括：

1. 不能可靠表达列重命名、类型变更、约束调整、索引调整等增量变更。
2. 不记录 schema 版本，无法确认某个数据库实例处于哪个结构版本。
3. 不支持受控回滚，错误变更后只能靠人工修复或重建数据库。
4. 不适合需要保留历史数据的共享环境；一旦后续模型演进，旧库升级路径不可审计。
5. 无法承载数据回填、分阶段发布、灰度切换等需要“结构变更 + 数据迁移”配合的场景。

因此，当前策略只能视为第一阶段早期开发期的临时方案，不能直接作为长期生产迁移机制。

## 第一阶段决策

当前不立即引入 Alembic。

理由：

1. 仓库仍处于后端基础能力建设阶段，数据模型尚未稳定。
2. 现阶段默认部署目标仍以本地 SQLite 和可重建测试库为主，`create_all` 能覆盖当前验证需求。
3. 在尚未出现明确 schema 演进需求前提前引入迁移脚手架，会增加维护负担，但暂时不能带来等价收益。

## 引入 Alembic 的触发条件

满足以下任一条件时，应优先把数据库迁移机制升级为 Alembic，并停止把 `create_all` 作为共享环境的主迁移手段：

1. 需要修改已存在表结构，而不是仅新增新表。
2. 需要保留现有 SQLite 或 PostgreSQL 业务数据，不能接受“删库重建”。
3. 出现测试环境之外的共享部署环境，例如长期运行的内网实例、预发布环境或正式环境。
4. 需要执行数据回填、历史字段迁移、默认值修正等伴随 schema 变化的数据迁移。
5. 多人协作下需要明确、可审计、可回滚的 schema 版本管理。

## 后续落地建议

当触发上述条件后，建议按以下最小边界推进：

1. 新增 Alembic 依赖、迁移配置和首个基线迁移。
2. 将应用启动期的 `create_all` 限制为开发/测试辅助能力，避免在共享环境自动改 schema。
3. 在 `README.md` 和 `scripts/verify.sh` 对应流程中补充迁移执行说明。
4. 对已有本地数据库给出一次性迁移或重建策略，避免旧库静默失配。
