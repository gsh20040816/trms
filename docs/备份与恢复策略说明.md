# 备份与恢复策略说明

更新时间：2026-04-28

## 当前范围

本文档只描述当前第一阶段部署基线下的最小备份与恢复策略建议，不代表仓库已经内置自动备份任务。

当前需要纳入保护范围的资产如下：

1. PostgreSQL 业务数据库：保存任务、成员、材料元数据、识别结果、校验结果、分摊、确认和审计日志。
2. S3 兼容对象存储 bucket：保存原始上传材料、导出产物和识别中间文件。
3. 原始材料对象：虽然物理上位于对象存储中，但业务价值高于可再生成的导出文件，应单独强调其恢复优先级。

当前不在本文档内展开的内容：

1. 自动备份调度实现。
2. 第三方云厂商的托管快照细节。
3. 密钥管理系统或跨地域容灾方案。

## 设计原则

1. 原始材料不可丢失。导出文件理论上可再生成，但原始发票、支付记录、比赛通知等上传材料不可依赖“重新收集”作为恢复方案。
2. 数据库与对象存储必须成对备份。只恢复数据库或只恢复对象文件都会导致 `storage_key`、导出任务和材料元数据失配。
3. 备份不能替代恢复演练。只有在隔离环境完成过一次恢复并核对结果，备份策略才算具备上线意义。
4. 生产环境不依赖容器本地临时目录。当前部署基线已经要求生产使用 PostgreSQL 和 S3 兼容对象存储，恢复策略也以这两类持久化介质为前提。

## 建议策略

### 1. PostgreSQL

建议至少同时保留两类备份：

1. 周期性逻辑备份：使用 `pg_dump -Fc` 导出，便于按库恢复和做离线校验。
2. 存储级快照或卷级备份：用于更快恢复整个实例或应对误操作后的完整回滚。

建议频率：

1. 每天至少一次逻辑备份。
2. 每次执行 Alembic 迁移或批量运维操作前，额外做一次即时备份。
3. 如共享环境每天都有活跃写入，建议再增加更高频的 WAL 归档或底层卷快照；若当前运维条件不足，至少先落实“每日逻辑备份 + 变更前即时备份”。

Compose 基线下可参考的逻辑备份命令：

```bash
mkdir -p backups/postgres
docker compose --env-file .env -f deploy/docker-compose.yml exec -T postgres \
  pg_dump -U "${TRMS_POSTGRES_USER}" -d "${TRMS_POSTGRES_DB}" -Fc \
  > "backups/postgres/trms-$(date +%F-%H%M%S).dump"
```

恢复演练时可参考：

```bash
createdb -U "${TRMS_POSTGRES_USER}" trms_restore_check
pg_restore -U "${TRMS_POSTGRES_USER}" -d trms_restore_check backups/postgres/<backup-file>.dump
```

## 2. 对象存储

对象存储备份至少应覆盖：

1. 原始材料对象。
2. 导出产物对象。
3. 识别中间文件或后续新增的衍生文件前缀。

建议策略二选一，条件允许时同时使用：

1. 开启 bucket 版本管理或底层快照能力。
2. 定期把 bucket 镜像到独立备份位置，例如另一套对象存储 bucket、离线磁盘或受控备份目录。

如果当前生产基线继续使用 MinIO，可参考 `mc mirror` 做对象镜像：

```bash
mc alias set trms http://127.0.0.1:9000 "${TRMS_MINIO_ROOT_USER}" "${TRMS_MINIO_ROOT_PASSWORD}"
mc mirror --overwrite trms/"${TRMS_STORAGE_S3_BUCKET}" /secure-backups/minio/"$(date +%F)"
```

若使用云厂商 S3 兼容服务，优先使用该服务提供的版本管理、生命周期和跨 bucket 复制能力，而不是只依赖单机磁盘拷贝。

## 3. 原始材料与导出产物的优先级

恢复优先级建议如下：

1. 第一优先级：原始材料。
2. 第二优先级：数据库元数据与审计日志。
3. 第三优先级：导出产物。

原因：

1. 原始材料是唯一事实来源，数据库可从备份恢复，但无法从导出文件反推完整原始票据。
2. 导出产物虽然最好一并备份，但在数据库和原始材料完好时，理论上可通过重新导出补回。

因此即使存储容量紧张，也不应只备份 `_exports/` 前缀而忽略原始材料对象。

## 建议保留策略

第一阶段先采用保守基线：

1. PostgreSQL 逻辑备份至少保留最近 7 份日备和最近 4 份周备。
2. 对象存储镜像或快照至少保留最近 7 天，并保留最近 1 个完整周备份点。
3. 迁移前即时备份至少保留到该次变更稳定验收完成。

若后续接入学校或实验室统一备份平台，应以平台的保留策略为准，但前提是不降低对原始材料的恢复能力。

## 恢复演练要求

上线前必须至少执行一次数据库与对象存储的恢复演练，且在隔离环境中完成以下核对：

1. 使用备份恢复出一套可启动的 PostgreSQL 数据库。
2. 恢复对象存储 bucket 或独立前缀中的样本原始材料和导出产物。
3. 启动 API/worker 后，确认 `/health` 正常。
4. 抽样核对材料记录、`storage_key` 对应对象、导出文件下载和至少一条审计记录可读。
5. 记录恢复命令、耗时、失败点、未覆盖风险和后续改进项。

本仓库当前只完成“策略说明”边界，尚未完成上述恢复演练；对应实操仍属于 `TASKS.md` 中后续独立任务。

## 当前缺口

截至本文档更新时，仍存在以下明确缺口：

1. 仓库未内置自动化备份调度脚本。
2. `./scripts/verify.sh` 尚未覆盖真实备份或恢复动作。
3. 尚未执行一次基于当前 Docker Compose 基线的数据库与对象存储恢复演练。
4. 尚未建立数据库记录数与对象存储对象清单的自动一致性核对脚本。

因此当前结论仅为“备份与恢复策略边界已明确”，不能表述为“备份恢复能力已验证完成”。
