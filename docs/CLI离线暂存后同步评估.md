# CLI 离线暂存后同步评估

日期：2026-04-29  
范围：第一阶段是否引入“CLI 离线暂存后同步”能力的评估，不直接实现功能

## 结论

- 不进入第一阶段实现范围。
- 归入后续阶段增强项；如果未来要做，必须先单独设计本地暂存安全边界和同步冲突语义，不能直接在现有 `submit` 命令上叠加隐式重试。

## 评估依据

1. 需求文档 `同济大学ACM竞赛报销收集系统需求分析文档_V0.2.md` 第 14.3 节已将“CLI 离线暂存后同步”列为 Could have，Q-011 也明确把它标为待确认问题，而不是第一阶段 Must / Should。
2. 架构文档 `同济大学ACM竞赛报销收集系统架构设计与技术选型文档_V0.1.md` 对 CLI 的第一阶段定位仍是“Token 登录 + 在线调用统一后端 API”的轻量提交渠道，没有定义本地任务队列、离线缓存加密或后台同步器。
3. 当前 CLI 实现是显式在线模型：
   - `src/trms_cli/token_store.py` 只维护本地 `session.json` 会话；
   - `src/trms_cli/cli.py` 的 `submit` 会立即读取本地文件、做本地预检查，然后直接请求 `/api/tasks/{task_id}/materials`；
   - `tasks`、`status`、`missing-materials`、`confirm-expense` 也都依赖在线读取最新服务端状态，没有离线快照或本地版本对账机制。

## 数据安全风险

CLI 离线暂存不是“把失败请求晚点再发”这么简单，它会把当前只存在于一次命令执行内的敏感数据，变成长期保存在成员本机上的待同步资产。

1. 原始材料会从“一次性读取后直接上传”变成“本地长期滞留”。
   如果只保存文件路径，同步时文件可能已经被修改、删除或替换；如果复制文件内容到本地队列，又会额外形成一份发票、支付截图、行程单等敏感材料副本。
2. 暂存清单至少需要保存任务编号、成员身份、材料类型、原始文件名等元数据。
   这些字段本身就能暴露参赛、报销和个人提交行为，不能当作普通无敏感性的缓存处理。
3. 当前本地会话存储只有 `session.json` 一处，且依赖 0700/0600 文件权限控制。
   一旦引入离线队列，就需要回答队列文件是否也采用同等保护、是否允许明文保存、同步成功后何时删除，以及失败重试历史是否需要脱敏保留。
4. 若把 access token、refresh token 或完整请求头跟离线队列绑在一起，会扩大凭据泄漏面。
   当前实现只在会话文件里保存 token；离线同步若为了“自动重试”复制凭据到另一份本地结构，会直接破坏现有最小安全边界。

## 同步冲突风险

离线暂存的核心问题不是上传动作本身，而是“离线时刻看到的任务状态”与“真正联网同步时的服务端状态”之间可能已经不一致。

1. 任务可能已截止、关闭或不再对该成员可见。
   当前 `tasks` 命令只在线返回当前可提交任务；离线排队后再同步，服务端可能已经拒绝该任务接收新材料。
2. 成员绑定身份可能已变化。
   当前 `submit` 固定使用本地会话中的 `member_id` 和 bearer 身份；如果成员重新登录、切换环境或账号绑定关系变化，旧离线队列可能把历史材料提交到错误身份上下文。
3. 本地文件内容可能在暂存后发生变化。
   若队列只记路径，不同于当时用户以为“已经整理好待同步”的那份文件；若队列复制内容，又回到前面的敏感副本问题。
4. 批量同步会把现有 `partial_success` 语义复杂化。
   当前 CLI 已支持“本地预检查失败 + 服务端批量部分成功”的明确结果；离线队列再加重试后，还要回答：
   - 哪些文件已经成功同步、哪些仍待重试；
   - 重复 hash / 重复发票被拒绝时是否自动移出队列；
   - 多次重试后如何向用户展示一份稳定、可审计的结果。
5. 服务端识别、校验和确认状态都是异步变化的。
   即使离线材料最终补传成功，成员也不能在离线模式下获得可靠的“任务当前还缺什么、哪些金额需要确认”的真实状态；因此离线暂存只能解决“晚点上传”，不能提供真正离线闭环。

## 当前不适合进入第一阶段的原因

1. 第一阶段 CLI 主目标已经完成在线闭环。
   当前仓库已经具备登录、任务查询、批量上传、状态查询、缺失材料查看和费用确认的在线主链路；离线暂存只改善弱网体验，不是当前主链路阻塞能力。
2. 它会引入新的本地状态机和恢复语义。
   需要设计待同步队列、同步结果回写、失败重试、人工清理、跨平台目录位置、文件生命周期和错误提示，不再是一个简单参数增强。
3. 它的风险主要落在本地安全与一致性，而不是后端业务规则。
   当前第一阶段更应该优先保证统一鉴权、审计、真实外部接入和生产部署边界，而不是先把敏感材料长期缓存到成员设备上。
4. 需求文档本身也没有给出离线模式的产品语义。
   例如是否允许成员离线编辑待同步清单、是否支持离线查看历史任务、同步冲突由谁裁决，这些都还是未定问题，不适合在本轮直接实现。

## 后续阶段建议边界

如果后续要做，建议先拆一个纯设计任务，至少先回答以下问题，再决定是否实现：

1. 暂存的是“文件路径引用”还是“不可变文件副本”，以及各自的删除策略。
2. 队列文件是否需要独立加密或至少独立权限约束，避免与普通缓存混放。
3. 同步动作是否必须显式由用户触发，而不是后台静默自动重试。
4. 任务关闭、身份变更、重复材料和部分成功时，本地队列如何收敛成可解释结果。
5. 是否需要先做只读草稿能力，再做真正的联网同步执行器。

## 本轮决定

- 第一阶段维持现状：CLI 继续作为在线提交渠道，不引入本地离线材料队列。
- 后续如要推进，应先新增“CLI 离线队列与同步冲突模型设计”任务，而不是直接修改现有 `submit` 命令。
