# 历史成员信息复用评估

日期：2026-04-29  
范围：第一阶段是否引入“历史成员信息复用”能力的评估，不直接实现功能

## 结论

- 不进入第一阶段实现范围。
- 归入后续阶段增强项，与“历史比赛模板和成员复用”保持一致。

## 评估依据

1. 架构文档 `同济大学ACM竞赛报销收集系统架构设计与技术选型文档_V0.1.md` 第 13.3 节已经将“历史比赛模板和成员复用”列为后续阶段能力。
2. 当前任务创建主链路只接受显式 `member_ids` 列表：
   - 后端 `TaskRow.member_ids` 仅保存任务内成员编号集合；
   - `TaskCreateInput.member_ids` / `TaskMembersUpdate.member_ids` 也仅表达当前任务成员列表；
   - 管理员端创建页 `admin-task-create.tsx` 仅提供手工录入成员编号的最小闭环。
3. 当前账号体系中的 `UserAccountRow.member_code` 只能表达登录账号与成员编号的绑定，不等同于可直接复用的历史成员主数据。

## 当前不适合进入第一阶段的原因

1. 缺少稳定的历史成员主数据模型。
   当前系统没有“成员档案”实体，只有任务内 `member_ids` 和账号表中的 `member_code`。如果要复用历史成员，至少需要先定义成员主数据来源、唯一键、展示名、失效策略和与登录账号的一对一 / 一对多边界。
2. 会污染当前任务创建主路径。
   第一阶段的任务创建已经围绕“管理员手工填写成员名单”建立测试和前端闭环。此时加入历史候选成员选择、搜索、回填、纠错和去重，会扩大管理员创建页和任务成员管理接口的职责。
3. 身份一致性风险尚未收口。
   当前系统还同时存在任务成员编号、账号 `actor_id`、账号 `member_code`、Telegram/邮件绑定成员编号等多套身份映射。若没有先建立成员主数据和去重规则，直接复用历史成员容易造成错绑、重号或历史脏数据扩散。
4. 第一阶段收益不高于引入复杂度。
   第一阶段目标是确保“任务创建 -> 提交 -> 识别 -> 校验 -> 分摊 -> 确认 -> 导出”主链路稳定。历史成员复用主要优化录入效率，不属于当前最小闭环的阻塞能力。

## 后续阶段建议边界

若后续要做，建议按以下顺序单独拆任务，而不是直接往现有创建流程里堆补丁：

1. 先建立成员主数据边界。
   明确是否引入独立 `member_profiles` / `member_directory`，以及它与 `user_accounts.member_code`、任务成员列表、渠道绑定之间的同步规则。
2. 再做只读复用。
   优先支持管理员在创建任务时“从历史成员中选取并回填成员编号”，不要一开始就支持自动覆盖、自动合并或隐式更新历史档案。
3. 最后再做模板化增强。
   将“历史成员复用”与“常见比赛模板”联动评估，避免分别引入两套相似但不一致的预填机制。

## 本轮决定

- 第一阶段维持现状：管理员继续手工维护任务 `member_ids`。
- 后续如要推进，应该先新增“成员主数据边界评估 / 设计”任务，再决定是否进入实现。
