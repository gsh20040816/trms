# Browser Use 后续阶段方案评估

更新时间：2026-04-29

## 1. 评估目标

本评估用于回答三个问题：

1. TRMS 后续是否值得引入 Browser Use 或其他浏览器自动化来辅助录入学校财务系统；
2. 如果后续要做，必须把哪些风险、人工确认点和执行退出条件写成硬边界；
3. 这项能力应以什么最小形态落地，才不会污染当前第一阶段主链路。

本轮只做评估，不实现 Browser Use，不新增依赖，也不保存财务系统登录态。

## 2. 当前现状

当前仓库已经具备“财务系统录入前”的整理能力，但没有任何财务系统自动化实现：

1. 需求文档 FR-011 明确写为第一阶段 `Won't have`，只允许后续阶段评估。
2. `docs/第一阶段范围边界说明.md` 已明确：
   - 第一阶段不自动登录财务系统；
   - 不自动填表；
   - 不自动点击最终提交；
   - 不保存财务系统账号密码、Cookie 或长期会话。
3. 当前代码已经能生成可供人工录入的导出结果：
   - `src/trms_backend/domain/exports.py` 已实现 `finance_draft` 导出构建；
   - `src/trms_backend/application/export_async_jobs.py` 已能异步生成导出产物；
   - 这意味着后续自动化若存在，输入来源应是“已确认的导出草稿”，而不是原始 AI 识别结果。
4. 当前仓库已有基础审计与导出任务记录，但还没有“财务系统自动填报动作”的专用审计模型、回放模型和失败恢复模型。

因此，当前系统适合继续把自己定位成“生成可人工录入的财务草稿”，而不是“服务器代替管理员登录并提交财务系统”。

## 3. 当前结论

结论：**后续阶段可以评估 Browser Use，但只能作为“管理员在场的辅助填表器”，不能设计成无人值守自动提交器。**

具体判断如下：

1. 第一阶段仍然不实现 Browser Use，当前结论不变。
2. 即使进入后续阶段，自动化也只能消费：
   - 已完成任务复核后的 `finance_draft` 导出；
   - 已经过管理员确认的字段映射结果；
   - 已显式选择的目标财务页面上下文。
3. 不应让 Browser Use 直接读取未确认的识别结果、在后台长期保管登录态，或在无人确认时自动点击最终提交。
4. 更合理的后续形态是：
   - 由管理员在受控本地环境启动自动化；
   - 自动化负责“辅助定位页面、填充字段、停在待确认状态”；
   - 最终提交动作保留给管理员人工确认。

## 4. 主要风险

如果后续要做 Browser Use，至少要正视以下风险，而不是把它当成普通导出功能的自然延伸：

### 4.1 数据事实漂移风险

TRMS 内的 `finance_draft` 只是“待录入草稿”，财务系统页面上的真实字段、校验规则和当日填写上下文可能已经变化。

风险表现：

1. 管理员在 TRMS 内复核后又改了任务数据，但自动化仍使用旧草稿；
2. 财务系统页面拆分或合并字段，导致一对一映射失真；
3. 财务系统存在页面端二次校验、自动计算或隐藏默认值，最终结果与 TRMS 草稿不一致。

### 4.2 页面脆弱性与反自动化风险

学校财务系统不是为自动化接口设计的，页面结构、登录流程、验证码和防刷策略都可能变化。

风险表现：

1. DOM 结构、按钮文案或 iframe 层级变化导致步骤失效；
2. 登录流程新增验证码、短信校验或统一身份认证跳转；
3. 目标页面出现多条相似字段，自动化无法稳定判断应写哪一项。

### 4.3 不可逆误操作风险

财务系统中的“保存”“提交”“送审”常常是高风险动作，一旦误点可能生成错误单据，甚至影响后续人工流程。

风险表现：

1. 将金额填错到错误费用栏位；
2. 把团队任务写到错误项目编号或错误报销人名下；
3. 重复创建单据或覆盖管理员当前手动编辑中的内容。

### 4.4 凭据与登录态泄露风险

财务系统登录态比 TRMS 自身账号更敏感，不应被后端服务、worker 或仓库存储长期持有。

风险表现：

1. 服务端保存明文密码、Cookie、浏览器 profile 或可复用 session；
2. 调试日志、异常栈或截图中泄露真实财务页面敏感信息；
3. 多管理员共用同一自动化运行容器，导致账号边界混淆。

### 4.5 审计和追责不足风险

“自动填过了”这种模糊结论无法满足高风险业务需要，必须能够回答是谁、何时、根据哪版草稿、向哪个页面填了哪些字段。

如果没有专门的审计与回放边界，后果是：

1. 出错后无法判断是草稿错、映射错还是自动化执行错；
2. 无法证明最终提交前是否真的有人确认过；
3. 无法在页面变化后快速禁用有风险的流程。

## 5. 必须的人工确认点

后续如果真的实施，至少要保留以下人工确认点；缺一项都不应放行执行：

1. 执行前确认任务版本。
   管理员必须确认本次使用的 `finance_draft` 导出版本、任务编号、报销人和项目编号，没有新数据变更待同步。
2. 执行前确认目标页面。
   管理员必须确认当前打开的是正确的财务系统入口、正确账号、正确报销类型，而不是让自动化自己猜测业务上下文。
3. 字段映射预览确认。
   自动化执行前应展示“TRMS 字段 -> 财务页面字段”的预览摘要，尤其是金额、项目号、人员、附件数量和备注。
4. 高风险写入前确认。
   当自动化准备创建新单据、追加明细行、上传附件或覆盖已有页面内容时，必须再次由管理员确认。
5. 最终提交前确认。
   自动化最多停在“已填好待检查”状态；是否点击最终提交、送审或确认按钮，必须由管理员手动确认。

换言之，Browser Use 在这里更像“半自动填表助手”，而不是“全自动报销提交器”。

## 6. 执行退出条件

后续若实现，该能力必须有明确的“立即停止并返回人工处理”的退出条件，不能靠模糊 fallback 硬顶过去：

1. `finance_draft` 版本变旧。
   任务数据版本、导出版本或管理员复核状态在执行前后发生变化时，立即停止。
2. 页面结构或关键控件无法稳定识别。
   找不到目标字段、按钮、表格行或页面标题不匹配时，立即停止。
3. 发现未确认或歧义字段。
   金额、成员、项目号、报销类型、附件类别等关键字段出现多候选、空值或冲突时，立即停止。
4. 登录流程进入验证码、二次认证或异常跳转。
   不尝试绕过，不缓存凭据，直接退出交给管理员人工处理。
5. 检测到已有未保存页面状态或潜在重复单据。
   自动化无法确定“继续是否会覆盖现有人工操作”时，立即停止。
6. 任一步骤产生未建模弹窗、报错或服务端返回异常。
   不静默重试到看起来成功，而是显式失败并把上下文交还给管理员。

这些退出条件不是“体验优化项”，而是高风险业务的最低安全边界。

## 7. 后续阶段的最小落地边界

如果后续真的要推进，建议按下面顺序拆任务，而不是一步做到“自动提交财务系统”：

1. 先固化自动化输入。
   把 `finance_draft` 导出补成更稳定的字段清单和版本快照，让自动化只依赖明确结构化输入。
2. 再建立映射预览与人工确认页。
   在 TRMS 内先让管理员确认“准备写入财务系统的字段摘要”，而不是让 Browser Use 直接读全量任务数据。
3. 再做受控本地执行器。
   优先让自动化运行在管理员本地或受控跳板环境，避免把财务登录态放进后端 API/worker 基础设施。
4. 最后才评估是否需要更深的页面自动化。
   包括多页跳转、附件上传、明细拆分、保存草稿等；最终提交按钮默认继续保留人工点击。

这条路径的核心目的是把风险分层，而不是把导出逻辑、审计逻辑和浏览器自动化一次性耦合在一起。

## 8. 不保存财务系统登录态的明确边界

后续即使引入 Browser Use，仍必须坚持以下约束：

1. 不把财务系统账号密码写入仓库、数据库、日志或 `.env.example`。
2. 不在后端服务端长期保存 Cookie、浏览器 profile、刷新 token 或其他可复用会话材料。
3. 若管理员在本地受控环境临时登录，登录态只允许保留在该次执行上下文中，并在执行结束后主动清理。
4. 任何截图、录像、错误日志和审计摘要都必须避免泄露完整凭据和无关财务敏感信息。

如果做不到这一点，就不应该进入实现阶段。

## 9. 当前建议

基于需求、现有架构和当前代码事实，当前建议是：

1. 第一阶段继续维持“只导出财务草稿，不做 Browser Use”的边界。
2. 后续阶段若要评估 Browser Use，应先新增“财务填报映射预览 + 专用审计模型 + 受控本地执行器设计”任务。
3. 在没有专门人工确认链、退出条件和临时登录态治理前，不要把 Browser Use 接入现有后端 worker，更不要设计成无人值守自动提交。

本轮结论不是“永远不做 Browser Use”，而是“只有把它收敛为受控、可审计、显式人工确认的辅助工具时，才值得进入后续阶段实现”。
