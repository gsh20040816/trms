# 报销交互简化改造方案

更新时间：2026-04-30

本文档面向当前系统的最终产品目标：成员只上传发票和附件，由 AI 自动识别类别、校验缺失材料并给出最少必要确认；管理员只处理异常，最终直接下载整理好的报销材料包。

本方案只做产品与技术改造分析，不代表相关功能已经实现。

## 1. 当前判断

当前系统已经具备不少底层能力：

1. 成员端已经支持免选材料类型上传，上传后由识别链路收敛材料类型。
2. AI 识别链路已经拆成“分类”和“按类别提取字段”两阶段，支持文本 PDF、扫描 PDF 和图片路径。
3. 后端已经有附件单候选自动归票、多候选待关联摘要、共享发票摘要、成员批量提交和撤回 API。
4. 成员工作台已经能展示本人发票、共享发票、识别字段、材料类型、分摊、缺失材料和待关联辅助材料。
5. 管理端已经有任务推进、复核、导出任务和真实 merged PDF 导出。

因此后续重点不是重新设计一套大架构，而是把已有能力重新编排成更短的业务路径。当前交互繁琐的根因主要是：

1. 成员仍要理解“上传、识别、附件关联、分摊、确认、提交”多个状态，而不是只看到“下一步还差什么”。
2. 工作台虽然收口到单任务上下文，但仍保留多个操作区，用户需要自己判断哪张发票已经可以交给管理员。
3. 待关联附件已有提示，但用户还缺少直接选择发票并完成关联的低摩擦写操作。
4. 管理员仍要分别理解复核页、导出页、多个导出产物和任务状态，缺少“材料包是否就绪”和“一键下载完整包”的主动作。
5. 前端当前为了拼出工作台视图，需要多次读取发票、识别、校验、附件、分摊和确认数据，容易让页面逻辑继续变重。

## 2. 目标交互

### 2.1 成员端目标流程

目标流程应收敛为四步：

1. 选择比赛任务。
2. 批量上传发票和附件，不要求提前选择材料类型。
3. 系统自动识别、分类、关联附件、校验缺失项，并只列出需要成员处理的事项。
4. 成员确认可提交的发票，一键提交给管理员；如管理员尚未进入复核阶段，可撤回修改。

成员不应被要求理解内部状态名，也不应需要主动在多个页面之间拼接上下文。界面默认应回答三个问题：

1. 这批材料系统处理到哪一步了？
2. 哪些发票已经可以提交？
3. 还有哪些发票因为识别、附件、分摊或确认问题不能提交？

### 2.2 管理端目标流程

管理员目标流程应收敛为三步：

1. 打开任务，先看整体就绪度：待识别、待关联、缺附件、待确认、可复核、可导出。
2. 只进入异常队列处理问题材料；正常材料不需要逐张人工点开。
3. 所有门禁通过后，点击一次生成并下载完整材料包。

管理员下载的材料包应是面向真实提交的交付物，而不是一组需要二次整理的零散导出按钮。

## 3. 推荐方案

### 3.1 成员工作台改成“待处理事项 + 可提交发票”主结构

保留当前单任务工作台，但调整默认信息架构：

1. 顶部固定展示任务处理进度，而不是先展示全部发票细节。
2. 第一屏展示“待处理事项”和“可提交发票”两组列表。
3. 已可提交的发票默认支持批量勾选，成员一键提交给管理员。
4. 不可提交的发票按阻塞原因分组：识别中、识别失败/待确认、附件待关联、缺失材料、分摊未完成、确认未完成。
5. 发票详情仍保留，但作为处理某个阻塞项时展开的上下文，而不是默认要求成员逐张浏览。

可行性：

1. 后端已有批量提交和撤回 API，可直接支撑“可提交发票”区。
2. 工作台已有识别、校验、缺失材料、分摊和确认数据来源，可先在前端聚合出可提交状态。
3. 后续应把前端聚合下沉为后端 `member-workbench-summary` 类接口，减少页面 N+1 请求和重复状态推导。

### 3.2 待关联附件增加“选择归属发票”动作

现状已经能告诉用户哪些附件没有安全归票，但多候选场景仍只能“查看候选发票”。下一步应补齐写操作：

1. 对多候选附件，成员可在候选发票中选择一张并确认关联。
2. 对无候选附件，引导用户先补录或上传发票。
3. 关联成功后立即刷新该发票校验结果和缺失材料状态。

可行性：

1. 后端已有 `PUT /api/invoices/{invoice_id}/supporting-materials/{material_id}` 能力。
2. 该接口当前需要先补齐成员身份、任务成员关系和材料提交人边界，再接入成员端按钮，避免成员把他人附件错误挂到自己发票。
3. 自动关联仍应只保留单候选安全规则，多候选必须人工选择，不能用模糊推断静默绑定。

### 3.3 上传后改为“自动处理队列”而不是“上传结果列表”

上传成功后，界面应从“逐文件结果”转向“系统正在处理这批材料”的状态：

1. 上传区仍显示部分成功和失败原因，但不把它作为主流程终点。
2. 对成功材料展示处理阶段：已接收、识别排队中、识别完成、已归票、需要处理。
3. 对识别服务未配置、排队等待 worker、识别失败分别给出不同说明。
4. 识别完成后自动刷新待处理事项，不要求用户手动判断是否该去缺失材料页或确认页。

可行性：

1. 当前上传响应已有识别调度信息，材料状态和识别任务状态也已经可查询。
2. 可以先在前端做短轮询或手动刷新；生产侧不应长期依赖高频轮询，后续可再评估事件推送。

### 3.4 管理端增加“任务就绪度总览”

管理员进入任务后，第一屏应先展示门禁状态，而不是直接要求进入各模块：

1. 材料处理：待识别、识别失败、低置信待确认。
2. 附件完整性：待关联附件、缺失材料、异常校验。
3. 金额确认：分摊未完成、成员未确认、有异议。
4. 导出准备：是否已满足生成材料包条件，若未满足列出阻塞原因。

可行性：

1. 后端已有复核摘要、缺失材料、导出 boundary 和任务成员状态等数据。
2. 第一版可以由前端组合现有接口；后续应形成稳定的任务就绪读模型，供管理员首页、任务详情和导出页复用。

### 3.5 管理员导出改成“一键完整材料包”

在现有导出体系上新增一个主导出物：`reimbursement_package`。它应生成一个 ZIP 包，至少包含：

1. `merged-printing.pdf`：当前真实合并打印 PDF。
2. `reimbursement-summary.csv`：报销汇总表。
3. `member-details.csv`：成员明细表。
4. `invoice-details.csv`：发票明细表。
5. `missing-materials.csv`：缺失材料清单，若导出时为空也保留空表。
6. `finance-draft.json`：财务填报草稿。
7. `manifest.json`：材料包清单、任务数据版本、生成时间、导出人、每个文件的 hash、仍存在的 warning。

后续支持 XLSX 后，可以把 CSV 替换或并存为 XLSX。但第一版不要为了等待 XLSX 阻塞“一键材料包”，因为当前 CSV、JSON 和 merged PDF 已经能复用现有导出能力。

可行性：

1. 当前导出任务已经支持异步执行、数据版本快照、产物存储和下载。
2. `reimbursement_package` 可以复用现有导出构建函数，再用 ZIP 容器打包，不需要改变核心业务模型。
3. 导出失败必须指出具体子产物或材料编号，不能生成残缺包后伪装成功。

### 3.6 AI 只减少人工录入，不替代最终确认

为了避免把识别错误包装成自动化成果，AI 相关交互边界应保持清楚：

1. AI 可以自动分类、抽取字段、建议费用类型、生成缺失材料提示。
2. 关键字段低置信或冲突时必须进入待确认。
3. 系统可以自动把“满足全部门禁”的发票放入可提交列表，但成员提交给管理员仍应是显式动作。
4. 管理员最终复核和导出仍以规则门禁和审计记录为准，不因为 AI 输出看起来完整就跳过校验。

## 4. 最小任务拆分建议

建议按以下顺序拆成可验证的小任务：

1. 在成员工作台展示批量提交与撤回区，直接消费已有提交/撤回 API。
2. 补齐附件手动关联 API 的 bearer 身份、任务成员和提交人权限边界。
3. 在待关联辅助材料区增加“选择候选发票并关联”按钮。
4. 把成员工作台默认结构调整为“待处理事项 / 可提交发票 / 问题发票”，弱化默认全量详情浏览。
5. 新增成员工作台聚合读模型，后端一次返回发票可提交状态、阻塞原因、附件关联状态和确认状态。
6. 上传成功后接入处理状态刷新，让用户看到系统正在识别、归票和校验，而不是停在上传结果列表。
7. 新增管理员任务就绪度读模型，统一输出待识别、待关联、缺附件、待确认和导出阻塞原因。
8. 管理员任务详情第一屏接入就绪度总览和异常优先队列。
9. 新增 `reimbursement_package` 导出类型，先打包 CSV、JSON、merged PDF 和 manifest。
10. 导出页主按钮改成“生成完整材料包”，原有单项导出下沉为高级操作。
11. 在 UX 测试中补充真实主流程验收：成员批量上传后只处理系统列出的待办，管理员最终下载一个完整材料包。

## 5. 不建议的方向

1. 不建议让成员重新承担材料类型、费用类型、附件清单的手动填写责任；这会回到旧流程。
2. 不建议用 AI 自动静默处理多候选附件归属；一旦绑错，后续校验和材料包都会被污染。
3. 不建议在没有任务数据版本和 manifest 的情况下提供“一键下载”，否则管理员无法知道材料包对应哪次数据状态。
4. 不建议把 Browser Use 或财务系统自动录入混入本轮交互简化；第一阶段目标仍是录入前整理材料。
5. 不建议为追求少点击而自动替成员提交给管理员；成员提交应是明确交接动作，便于审计和撤回边界控制。

## 6. 验收口径

后续实现完成后，至少应满足以下验收口径：

1. 成员上传一批发票和附件后，不需要预选材料类型，也不需要跳转多个页面查状态。
2. 系统能明确列出“可提交发票”和“不能提交的原因”。
3. 多候选附件不会静默误绑，成员能在候选发票中显式选择归属。
4. 成员可以批量提交已就绪发票，并在管理员进入后续阶段前撤回。
5. 管理员能在任务页看到材料包是否就绪，以及剩余阻塞项。
6. 管理员能下载一个完整材料包，包内包含打印 PDF、汇总/明细/缺失清单、财务草稿和 manifest。
7. 所有自动识别、人工更正、附件关联、提交、撤回和导出下载都有可追溯记录。

## 7. 风险与控制

1. AI 识别误判风险：继续使用结构化校验、低置信待确认和人工更正，不把 AI 输出当最终事实。
2. 附件误关联风险：只自动处理单候选，多候选必须人工选择，并记录审计。
3. 权限泄露风险：共享发票只展示基础元数据和分摊摘要，不暴露原始附件、支付截图全文或识别原始响应。
4. 材料包过期风险：导出任务必须绑定任务数据版本；数据变化后旧包明确标为非最新。
5. 前端复杂度风险：短期可以组合现有接口，但中期必须下沉为聚合读模型，否则工作台会继续膨胀。

## 8. 当前结论

可行的最小路线是先不改大架构，沿着现有能力做三件事：

1. 成员端把“能提交什么、还差什么”放到第一屏，并接入批量提交/撤回。
2. 附件关联从“提示”补齐到“可直接处理”，但坚持多候选人工选择。
3. 管理端把多个导出物收敛成一个带 manifest 的完整材料包。

这条路线能最大限度复用当前代码，同时直接对应用户最终目标：成员少填少判断，管理员少整理少拼包。
